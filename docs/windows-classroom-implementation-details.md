# Windows 局域网课堂版实施细则

> 更新时间：2026-05-13  
> 目标分支：`future/windows-classroom`  
> 基础分支：`future/windows-base`  
> 适用范围：一台 Windows 主机在局域网内供至少 50 人使用，目标支撑 70 路视频并发的课堂/培训场景。

## 1. 实施目标

Windows 局域网课堂版的目标是让一台 Windows 主机作为局域网内学习平台服务端，供教室、机房或办公室内的多名用户通过浏览器访问。

典型使用方式：

1. 教师或管理员在 Windows 主机上启动课堂版。
2. 启动器显示本机局域网访问地址。
3. 学生在同一局域网内使用浏览器访问。
4. 平台支持课程浏览、视频播放、学习进度同步和后台管理。

课堂版不是公网服务器版，也不是集群版。它的边界是局域网内小规模课堂使用。

## 2. 分支约束

课堂版专属改动必须在：

```bash
git switch future/windows-classroom
```

共享基础能力先放在：

```bash
git switch future/windows-base
```

禁止在 `future/windows-classroom` 中实现单机版专属内容，例如：

- 只面向 localhost 的单机启动体验。
- 只服务个人本机使用的安装器假设。
- 与课堂 LAN 无关的桌面自动打开体验。

如果实现过程中发现课堂版和单机版都需要的能力，应先回到 `future/windows-base` 实现，再合并到 `future/windows-classroom`。

## 3. 当前基础层状态

`future/windows-base` 已完成的公共能力：

- 新增 `APP_EDITION` / `app_edition` 运行形态。
- 支持 `development`、`windows_local`、`windows_classroom`、`server`。
- Windows 版本默认回落到本地 SQLite 文件库。
- Windows 版本默认缓存后端解析为 `diskcache`。
- SQLite 文件库支持连接 `timeout`。
- 启动时自动创建运行目录。
- 启动时可配置 SQLite `busy_timeout`。
- `windows_classroom` 预留并接入 WAL 初始化。
- 新增运行配置与缓存抽象测试。

课堂版后续重点是 LAN 访问、视频/静态资源、学习进度写入频率和课堂规模边界。

## 4. 运行配置契约

课堂版必须使用：

```env
APP_EDITION=windows_classroom
```

推荐默认配置：

```env
APP_EDITION=windows_classroom
HOST=0.0.0.0
PORT=8000
CACHE_BACKEND=auto
SQLITE_BUSY_TIMEOUT_MS=30000
```

数据库默认不要求用户配置：

```text
未设置 DATABASE_URL -> 自动使用本地 SQLite 文件
```

课堂版必须显示局域网访问地址，例如：

```text
http://192.168.x.x:8000
```

如果获取不到局域网地址，应至少显示：

- 本机访问地址。
- 当前监听端口。
- 提示用户检查防火墙或网络连接。

## 5. 数据库实施细则

### 5.1 数据库选择

课堂版第一阶段仍使用 SQLite 文件数据库，不要求 Windows 用户安装 MySQL。

原因：

- 避免 Windows 用户接触数据库服务。
- 降低教室现场部署复杂度。
- 支持小规模局域网读多写少场景。

但课堂版必须明确边界：SQLite 不是大规模并发写入数据库，不能把它当作公网多人在线服务器数据库。

### 5.2 SQLite WAL

课堂版必须启用：

```sql
PRAGMA journal_mode=WAL;
```

并配置：

```sql
PRAGMA busy_timeout=30000;
```

目的：

- 提升读写并发体验。
- 减少短时间写锁导致的失败。
- 让多学生同时浏览课程时更稳定。

### 5.3 写入节流

课堂版最容易出问题的是高频学习进度写入，而不是普通课程浏览。

学习进度同步原则：

- 不允许每秒写一次数据库。
- 播放中按 10～30 秒间隔同步。
- 暂停时同步。
- 切换资源时同步。
- 页面退出或可捕获的关闭事件时尽量同步。

后续实现应优先检查：

- `UI/src/composables/useProgressSync.ts`
- `UI/src/store/learn.ts`
- `project_code/backend/app/api/v1/learning.py`
- `project_code/backend/app/services/learning_service.py`

## 6. 缓存实施细则

课堂版默认使用：

```text
diskcache
```

适合缓存：

- 首页课程列表。
- 课程详情基础信息。
- 分类列表。
- 标签列表。
- 公告列表。
- 权限码/角色权限。

禁止放入 `diskcache`：

- 视频文件本体。
- 大图片原文件。
- 大课件原文件。
- 上传文件原始内容。
- 视频分片流。

课堂版的性能关键不是把视频放进业务缓存，而是让视频和静态文件走正确的静态文件分发和浏览器缓存。

## 7. 视频与静态资源实施细则

课堂版的核心难点是视频/静态资源分发。

### 7.1 视频分发原则

视频文件不应由 FastAPI 业务接口整文件读取后返回。

禁止模式：

```text
Python 读取整个视频文件 -> 放入内存 -> 返回给浏览器
```

推荐模式：

```text
静态文件服务 / 反向代理 / 支持 Range 的文件响应 -> 浏览器按需拉取
```

必须支持：

- HTTP Range 请求。
- 视频拖动进度。
- 多个浏览器同时播放。
- 不把视频写入 `diskcache`。

课堂版的视频与大文件资源应遵守以下硬边界：

- 视频原文件不进入业务缓存。
- 课程视频不走整文件转发的 API 业务处理路径。
- 上传后的媒体资源应通过稳定静态路径访问。
- 前端构建产物可以长期缓存，但媒体资源更新必须有明确失效策略。

### 7.2 静态缓存

前端构建产物：

- JS/CSS 带 hash。
- 可长期缓存。

上传资源：

- 通过稳定静态路径访问。
- 视频和大课件不进入业务缓存。
- 后续可按文件名/hash 或版本策略处理更新失效。

### 7.3 FastAPI 边界

FastAPI 可以继续负责：

- API 权限判断。
- 课程/资源元数据。
- 上传入口。
- 学习进度。

FastAPI 不应成为课堂版视频大流量转发瓶颈。

## 8. LAN 启动器实施细则

课堂版启动器在宣布“启动成功”前，至少要验证：

1. 配置文件已加载，且 `APP_EDITION=windows_classroom`。
2. 目标端口未被占用。
3. 后端进程已启动。
4. 健康检查可达。
5. 本机访问地址与局域网访问地址都能展示。
6. 日志路径已明确输出。

如果局域网 IP 获取失败，启动器仍应展示本机访问地址、监听端口和防火墙提示，不应静默失败。

课堂版启动器职责：

1. 设置 `APP_EDITION=windows_classroom`。
2. 设置 `HOST=0.0.0.0`。
3. 启动后端服务。
4. 启动或提供前端静态服务。
5. 获取本机局域网 IP。
6. 显示访问地址。
7. 提示防火墙放行应用端口。
8. 失败时显示日志位置。

显示内容示例：

```text
学习平台课堂版已启动
本机访问：http://127.0.0.1:8000
局域网访问：http://192.168.1.23:8000
请让学生连接同一 Wi-Fi 或局域网后访问局域网地址。
```

## 9. 安全边界

课堂版只开放应用端口，不开放数据库端口。

必须保留：

- Bearer Token 登录态。
- 角色权限判断。
- 后台管理权限。
- 上传文件校验。
- 普通用户不能访问本地文件系统任意路径。

课堂版容量目标：

- 至少支撑 50 人同时访问。
- 最好能够支撑 70 路视频并发，前提是网络和磁盘条件足够。
- 如果实测无法稳定达到 70 路视频并发，应明确记录瓶颈位置，而不是把问题隐藏到缓存层。

课堂版不应承诺：

- 公网访问安全。
- 多校区跨公网访问。
- 100 人视频并发稳定。
- 集群扩容。

这些能力属于 Linux 服务器版或后续集群版。

### 9.1 容量验证口径

在文档和测试中，课堂版容量口径统一为：

- 基础验收：50 人轻量课堂可用。
- 目标验收：70 路视频并发尽力达到。
- 失败处理：如果视频并发不足，必须标注是网络、磁盘、静态服务还是 SQLite 写入压力导致。

课堂版实施和测试都要围绕这个口径展开，不再沿用更低的 10～50 人模糊表述。

## 10. 实施阶段

### Phase 1：基础配置接入

状态：已在 `future/windows-base` 完成。

内容：

- `APP_EDITION=windows_classroom`。
- SQLite 文件数据库默认值。
- diskcache 默认值。
- 运行目录自动创建。
- SQLite `busy_timeout`。
- SQLite WAL 初始化。

### Phase 2：课堂启动器

目标：让教师/管理员一键启动课堂版并看到访问地址。

可能新增：

- `start-windows-classroom.cmd`
- `config/windows-classroom.env`
- LAN IP 检测脚本或启动器逻辑。

实施细节：

- 读取 `config/windows-classroom.env`，默认设置 `APP_EDITION=windows_classroom`、`HOST=0.0.0.0`、`PORT=8000`、`CACHE_BACKEND=auto`。
- 启动前检查端口占用，失败时输出占用 PID。
- 获取局域网 IPv4 地址，排除 `127.0.0.1` 和虚拟网卡地址；无法判断时展示候选地址并提示人工确认。
- 等待健康检查通过后再输出“课堂版已启动”。
- 显示本机 URL、局域网 URL、日志路径和防火墙提示。
- 交付形态先按 `zip + launcher`，不要求本阶段完成安装器。

验收：

- 本机可访问。
- 同一局域网其他设备可访问。
- 失败时能看到日志位置和端口提示。
- `zip + launcher` 解压后可完成启动验证。

### Phase 3：学习进度节流

目标：避免 10～50 人同时学习时高频写数据库。

重点文件：

- `UI/src/composables/useProgressSync.ts`
- `UI/src/store/learn.ts`
- `project_code/backend/app/api/v1/learning.py`
- `project_code/backend/app/services/learning_service.py`

验收：

- 播放中不会每秒写库。
- 暂停、切换资源、退出时尽量保存进度。
- 后端测试覆盖重复/高频进度提交的处理。

### Phase 4：视频/静态资源优化

目标：课堂版视频可播放、可拖动、不会把大文件压进 Python 内存或 `diskcache`。

实施细节：

- 优先验证当前后端静态文件服务是否已经满足 Range；如果不满足，再补专用 Range 文件响应或切换到更合适的静态文件承载方式。
- 课堂版视频 URL 必须支持浏览器拖动进度和断点续拉。
- 视频文件、课件原文件、上传原文件都不能进入 `diskcache`。
- 前端学习页只消费稳定资源 URL，不把大文件内容通过业务 API 拉回前端。
- 70 路视频并发目标主要依赖磁盘、网卡、静态服务和视频码率；实现时必须能定位这些瓶颈。

验收：

- 视频支持拖动进度。
- 多浏览器同时访问同一视频不触发明显后端异常。
- 大文件不进入业务缓存。
- 70 路视频并发验证有明确结果：通过或记录瓶颈。

### Phase 5：课堂规模验证

目标：验证至少 50 人课堂可用，并尽力验证 70 路视频并发。

验证重点：

- 首页和课程详情读取体验。
- 视频播放和拖动。
- 学习进度写入频率。
- 后端日志错误率。
- Windows 主机 CPU、内存、磁盘和网络占用。
- 50 人基础验收和 70 路视频并发目标验收分开记录。

## 12. 验收标准

Windows 局域网课堂版达到可用状态时，应满足：

- 一台 Windows 主机可启动服务。
- 同一局域网其他设备可通过浏览器访问。
- 不要求安装 MySQL。
- 不要求安装 Redis。
- 数据库端口不暴露给局域网用户。
- 视频可播放并支持拖动。
- 学习进度不会每秒高频写入。
- 至少 50 人局域网课堂使用时不出现明显数据库写爆问题。
- 尽力支撑 70 路视频并发，并在未达成时记录明确瓶颈。

## 13. 明确不做

课堂版第一阶段不承诺：

- 公网部署。
- 100 人视频并发。
- Linux 集群能力。
- 多 Windows 主机共享数据库。
- 把视频文件放进 `diskcache`。
- 用 FastAPI 业务接口承载所有视频流量。

这些内容属于 Linux 服务器版、专业静态文件服务或后续扩容方案。
